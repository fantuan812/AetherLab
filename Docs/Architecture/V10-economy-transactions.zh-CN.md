# v10 商店、维修与待领奖励事务

## 实现范围

四个命令 BuyItem、SellItem、RepairItem、ClaimReward 已接入完整角色候选和异步协调器，共支持 17 种角色命令。库存、金币、耐久和领取记录在同一个 Profile BLOB/Revision 中提交。正式 NPC 会话、界面、磨损来源和游戏后端切换仍待接入。

## 定义与授权

Economy.json schema 1 只维护商人的商品、收购分类、维修能力和每点耐久费用。物品买卖价格仍唯一来自 Items.json，客户端命令不携带价格。Shop 出售三种补给并收购消耗品/材料；Armorer 出售五件皮甲、项链和戒指，收购装备类并维修，每恢复一点耐久费用 1 金币。该数值是本阶段配置，不是性能/玩法验收结论。Armorer 的正式地图/NPC 入口尚待接入。

解析器校验目录 schema、数量、重复 ID/产品、未知物品/分类、未定价商品和无效维修费。交易上下文由服务器解析当前目标与会话有效性，包括范围、视线、目标加载/存活与战斗限制；候选处理器要求目标 ID 与该上下文一致，不能使用所有商店商品的并集。

## 实例与经济不变量

AddNew 为新购/奖励生成定义默认状态。按真实格子顺序填充完整 StackKey 相同且未装备的堆，再占空格；锁定、品质、词条、绑定、耐久或任务状态不同均不合并。容量不足时整个候选失败，已填入的部分不发布。

出售调用 CanRemove，禁止已装备、锁定、绑定和任务限制物品，收购分类也必须匹配。部分出售保留剩余实例 GUID 和全部元数据。维修复用候选耐久规则，仅启用耐久且受损、当前角色可持有的物品可修理，费用按服务器定义计算；不会把禁用耐久的装备改成可磨损。

金额计算使用 int64 中间值，最终金币限定 0–10000000；购买余额不足、出售超出金币上限、修理费不足均失败。不会先扣钱再另存库存或耐久。

## 待领奖励

协议 v1 已有的 ClaimReward.DefinitionId 载荷使用固定键 Reward.<32 位 GUID>，只定位服务端 PendingRewards 记录，不接受客户端奖励数量或金额。解析必须是精确 GUID 格式。领取按稳定商品顺序构建全部物品和金币，再同时移除待领记录、加入 ClaimedRewardIds。

任何品类放不下、金币或已领账本达到上限都整笔失败，保留待领内容。原命令重试先回放持久回执；换一个命令 ID 也不能领取已结算奖励。未来网络协议若将奖励 GUID 拆成独立字段，必须升级协议并提供明确兼容处理，不能静默改变 v1 载荷。
