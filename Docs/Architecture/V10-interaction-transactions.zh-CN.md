# v10 首批交互事务与任务成长

## 本批接入

ExecuteInteraction 请求 v2 已进入真实异步 ProfileCoordinator。先读取持久回执，再读取角色并检查当前目标，随后以同一个 SQLite 读事务取得 Profile、World/Main 和角色版本索引。等待读取后重新解析目标；定义替换、卸载、遮挡、个人/世界/交互版本变化均拒绝。提交成功后再重读一致快照，旧会话或 Pawn epoch 不能发布。

当前有限处理器为 Register、BindInn、LearnStorySkills、ClaimQuest、ClaimSkillPoints。登记和据点绑定按现有任务门槛记录事实；导师依据 Skill 定义的故事门槛授予稳定 SkillId 的基础等级，不虚构学习付费账本。任务领取使用共享候选结算器。输入上下文里的 Claims、Evidence、点数可领取标记、故事能力可授予标记和处理器注册列表都不作为权限依据；以已读 Profile 和本单元实际实现重建。

每次交互原子推进 Profile 和读过的 World 版本，奖励、技能来源和完整命令回执同一提交。个人进度操作也比较世界版本，保证可追溯世界事实和奖励来自同一提交视图。回执保存目标交互版本；同 ID 重试直接恢复回执，不重新发奖励或生成来源事件。

训练对象生成、休息、交易/修理会话、招募、日常、物理设施、活动等尚未接入这些处理器。没有实现副作用的 Kind 返回 UnsupportedAction；本批没有用空成功或测试初始化替代真实服务。

## 任务奖励与成长配置

QuestProgression 只改经过校验的 Profile 候选，不直接写磁盘。服务器已经验证的个人/战斗事实才能 Observe；世界追溯事实还需校验 objective scope 和定义允许的来源。客户端不能直接指定任意 ObjectiveId 来完成任务。

任务结算先试装整份奖励。背包或金币容量不足时，整份金币/物品转入一个 PendingReward；完成标记、经验、据点绑定和技能点仍在同一候选内，避免满包卡住主线或只发一半奖励。待领空间、点数来源账本容量不足时整个候选失败，保留原状态。旧 ClaimReward 命令继续负责将待领记录完整兑现，并按 GUID 去重。

Progression.json schema 1 显式列出八个主线任务的点数：前两阶段 0，第 3～8 阶段各 2 点，共 12 点，足以支付现有四系各两次升级的 1+2 成本。该数值是首版内容配置，未来可调整。发放来源为 Quest.<QuestId>；已存在的来源保留实际历史数额，配置变化不补差、不重算。

新完成任务在结算候选内获得点数。已有完成任务的旧角色可通过导师的“领取任务成长点数”显式入口领取缺少的 v10 来源；重复操作没有新发放，也不再发旧任务金币/物品/经验。旧法术迁移函数仍只建立免费故事基础，不凭位掩码推断旧付费或退款。
