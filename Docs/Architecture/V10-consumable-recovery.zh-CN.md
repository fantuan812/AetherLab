# v10 消耗品事务与资源投递

## 本单元实际实现

类型化 UseItem 使用现有请求 v1：只携带实例 ID，一次使用一件。治疗量、冷却和食物安全时间取服务器 Rules.Uses，客户端不能提交数值。只有持有本 CommandId 资源屏障的服务器上下文可准备事务。拒绝死亡、满资源、冷却、锁定、任务实例、他人绑定、装备实例及不满足安全时间的使用；自己的绑定消耗品可用，收藏不会阻止显式使用。

库存扣除、Profile 版本推进、命令回执与一条 effects 投递在同一 SQLite 事务提交。部分堆保留 GUID、格子及全部状态，最后一件移除该实例。失败不发布候选；已提交但丢失应答时，原请求恢复原回执，不能再扣一件。

ACEF/1 使用有界显式小端编码（上限 512 字节），包含投递 ID、实例/定义、提交后 Profile 版本，以及使用前/后的 LifeId、资源版本、绝对生命/法力/体力、上限和 UTC 毫秒冷却。结果不在恢复时重读平衡表，不存“每次重试再加治疗”的指令。投递 ID 就是绑定 Profile 版本的 CommandId。解码拒绝非法范围、非有限值、跨生命、非连续版本、降资源、改上限、截断、尾随数据和未知版本。

## 资源所有者必须履行的接入契约

FAetherConsumableReceiver 在游戏线程持有资源状态和最多 128 条待确认投递记录。Reserve 取得精确前态屏障；持有期间 UpdateResources 返回 false。接入方必须延后整个资源相关动作及其死亡/伤害/消耗副作用，不能只丢弃资源写入，也不能绕过屏障直接改 ASC。构造 UseItem 上下文必须来自这个所有者。

Apply 只在前态完全一致时发布记录中的目标态，释放屏障并记住完整投递。相同 ID、相同内容重试不改资源；同 ID 不同内容冲突。这样已治疗后又受伤，丢失 ACK 导致的重试也不会覆盖伤害。无去重证据而资源版本已前进时保留待投递并报告冲突，不能擅自确认删除。

只有已确认未提交/回滚，才能 CancelUncommitted。Unavailable、超时和断连可能发生在提交之后，必须查询原命令回执/待投递，不能据此释放屏障。成功应用之后异步 AcknowledgeEffect；数据库确认删除后才 ForgetAcknowledged。遗留读批次在忘记 ID 后仍会因旧资源版本不匹配被拒绝。

## 明确的新生命恢复策略

本接收器提供显式 RecoverAtFullRespawn：新生命 LifeId、资源版本 0、所有资源已满、尚未进入战斗/开放输入，才能解决旧生命的 pending。调用方必须先等旧写任务结束，再读取该角色全部 pending，防止遗漏晚提交。批次全部验证后才原子记住投递并保留最晚冷却。全资源新生命初始化覆盖旧生命恢复需求，不把旧药效果叠加到新生命；随后新生命受伤，旧投递仍只返回 Replayed。

这不是任意生命切换时都可删除效果的许可。若未来采用保留残血跨重启的政策，必须恢复对应 LifeId/资源快照并使用精确版本应用，不能使用全资源分支。

## 异步投递调度补充

FAetherConsumableDeliveryPump 现已实现，游戏线程只轮询就绪 Future，每次 Poll 最多应用一条记录。Start 不接受重叠批次；每次 Poll 重新解析同一角色、会话、Pawn epoch 和接收器实例。角色身份也绑定在接收器内，不能把 Alice 的待投递交给 Bob。指针仅在本次游戏线程调用中使用，后台任务只捕获值。

整批读取先验证所有效果及唯一 ID，再开始应用。应用成功或相同内容重放后才入队 ACK；版本冲突、损坏批次、会话失效均保留尚未应用的记录。已入队 ACK 可以在旧会话失效后完成，因为其效果在有效代次下已经应用；不把迟到回调交给替换的资源所有者。

发起读取之前采样接收器已有的待确认 ID；完整 pending 查询中已经不存在的那些旧 ID，证明 ACK 已落盘，可回收内存去重槽。不会删除查询发起之后才产生的记录。新生命初始化成功但 ACK 失败时，结果 bFullRespawnRecovered=true；后续用普通模式恢复同一接收器，不能重复初始化。

调度器 Complete 表示本次读取批次已确认。正式登录恢复仍须先排空旧写者并维持输入/新写入屏障，再打开游戏；不能把一次查询当成阻止未来新提交的锁。资源动作排队和 ASC 接入仍未完成。
