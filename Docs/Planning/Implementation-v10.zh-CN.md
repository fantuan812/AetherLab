## 1. 完整交付范围与不可退让的标准

### 1.1 目标

将现有能运行、能验证部分规则的原型，完善成玩家可以正常游玩的角色系统与交互系统。交付不是“新增目录”“显示窗口”“动画能播放”，而是以下闭环全部成立：

**玩家操作 → 图形反馈 → 合法命令 → 权威规则执行 → 持久化与复制 → 真实角色/物品/技能变化 → 界面更新。**

本方案包含架构拆分、角色菜单、背包装备、道具拾取和丢弃、商店、详情弹层、线性技能成长、NPC 对话与引导、基础移动和战斗动作、MotionBricks 原生推理、人物重定向、联机生命周期、旧存档迁移、资源与发布验收。不能把任何一个主要功能只做到接口或实验地图后标记完成。

### 1.2 完整性的明确边界

默认产品范围是当前 AetherLab 的单人及最多四人合作玩法，首要正式客户端为 Windows x64，服务器覆盖 Windows x64 与 Linux x64。Linux 图形客户端、主机、移动端不自动纳入“已支持”；将来扩展必须补齐对应构建与性能矩阵。本方案不扩展到账号平台、支付、交易所、公会、竞技匹配或无限技能内容。

内容数量可以有限，系统链路不能缺失。每一种已开放装备槽、物品操作、技能类型、交互服务和动作状态，都必须有可取得、可实际使用的内容样本。地图、队伍等既有菜单入口也必须有正常图形页面，不能在重做背包后继续停留在开发日志界面。

### 1.3 正式 MotionBricks 交付，而非永久实验分支

`motion-bricks.cpp` 纳入正式客户端动作管线，在已声明支持的硬件配置上真实加载模型、执行推理、重定向并驱动角色。传统动画同样作为完整、长期维护的兼容路径保留，用于不适合生成的动作、故障、低配置和动画 LOD。

两者不是替代验收关系：

- 传统动作完整可用，不代表 MotionBricks 已接入。
- MotionBricks 能运行演示，不代表角色动作系统可发布。
- 任一强制交付项未通过，其工作包保持未完成；不能通过改名为“可选功能”消除要求。

### 1.4 可分阶段开发，不能分阶段降低最终标准

允许先接库、再接姿态、再接联机；这些是开发步骤，不是最终终点。技术检查和小场景测试用于降低风险，最终必须进入实际主线地图、正式角色、完整菜单和发布包中验收。

所有公开操作都必须可通过实际游戏输入触发。自动化测试、截图和日志是证明材料，不能代替玩家路径。

### 2.2 motion-bricks.cpp 带来的正确技术定位

这个仓库是 NVIDIA MotionBricks 的第三方 C++23/GGML 移植，提供 CPU 和 Vulkan 后端及稳定 C ABI；不是只能通过 Python 调用的项目，也不应将其称为 NVIDIA 官方 UE 插件。[M01]

已核查的关键契约：

| 能力/限制 | 对 AetherLab 的含义 | 依据 |
|---|---|---|
| 有状态 `mb_agent_*` 与无状态 `mb_model_infer` 两种入口 | 可以原生嵌入 UE；按控制职责选择接口 | [M03]、[M04] |
| 运行时不要求 Go、Web Demo、Python、Kimodo 或 SONIC | 游戏运行包不需要这些进程和服务 | [M03] |
| 输出为 G1Skeleton34，Y-up、米、30 FPS、局部 XYZW 四元数 | 必须做坐标转换、时间重采样及 G1→人物重定向 | [M03]、[M06] |
| 同一模型上的独立操作需要串行，包括不同 agent 与无状态请求 | 使用统一调度器；“模型不可变”不等于线程安全 | [M03] |
| batch 接口接受 1–64 个独立请求，但没有内置队列/等待窗 | 预算、优先级、合并与超时由 UE 适配层负责 | [M03]、[M04] |
| 无状态输出 24–64 帧、四帧为步长；边界姿态是条件而非严格约束 | 不能把生成结果直接当碰撞、手部接触或命中权威 | [M04] |
| ABI 1 内可新增符号，旧二进制可能没有新函数 | 同时校验版本清单与导出函数，不只比 ABI 数字 | [M03] |
| Windows 支持提交说明报告了 CPU-only 构建与测试 | 可作为集成起点；不是 AetherLab/Win64 Vulkan 已通过证明 | [M02] |
| 已发布 G1 模型和原始预处理风格；任意人物风格导入不是现成完成项 | 必须交付自己的受控姿态/风格生产工具与质量校验 | [M01]、[M06] |

**不能误用的指标：**README 中约 0.93 ms / 0.62 ms 的数据属于指定 CPU 上的 SONIC encoder+decoder，不是完整 MotionBricks 动作生成耗时；库级一致性测试也不是本游戏帧率证明。[M01]

## 3. 目标模块、目录与依赖边界

### 3.1 模块边界

最终采用少量具有明确编译边界的模块，模块内部按功能分目录。不为每个按钮或能力另建插件。

| 模块 | 责任 | 不允许承担 |
|---|---|---|
| `AetherCore`（新增） | 稳定 ID、结果类型、共享契约、Gameplay Tags、最小公共定义 | Widget、具体 Character、GameMode、推理库 |
| `AetherGameplay`（新增） | 库存、技能、任务、交互、角色动作、世界服务及权威用例 | 玩家 UI 绘制、第三方原生句柄直接管理 |
| `AetherEquipment`（保留并完善） | 装备槽适配、外观附着、装备定义与变化通知 | 金币/背包归属、任务完成、独立重复扣费 |
| `AetherUI`（新增） | CommonUI/UMG 页面、ViewModel、图标、预览、弹层 | 直接修改档案、决定伤害和任务奖励 |
| `AetherLab`（瘦身） | 主模块启动、具体模式/地图装配与依赖注入 | 所有服务的具体算法重新堆积 |
| `AetherEditor`（新增，Editor-only） | 资产校验、导入、迁移辅助、编辑器批处理 | 被客户端或服务器运行时反向依赖 |
| `ReactiveWorld`（保留插件） | 通用反应模拟与世界物理机制 | 技能树、装备 UI、某个具体主线任务 |
| `AetherMotion`（新增插件） | 原生库桥接、推理调度、姿态输出及编辑器节点 | 背包、主线、战斗伤害、服务器物理替代 |

目标依赖方向：

```text
AetherLab（装配根）
  ├─ AetherUI ───────→ AetherGameplay 公共查询/命令接口
  ├─ AetherGameplay ─→ AetherCore
  │        ├────────→ AetherEquipment ─→ AetherCore
  │        ├────────→ ReactiveWorld
  │        └────────→ AetherMotionRuntime ─→ MotionBricksNative
  └─ 具体地图与角色配置

AetherEditor / AetherMotionEditor → 对应 Runtime
所有 Runtime ✕→ Editor
AetherMotionRuntime ✕→ AetherGameplay / AetherLab / AetherUI
AetherCore ✕→ 以上具体实现模块
```

这里箭头表示编译依赖，不是事件传播方向。跨系统事件通过类型化委托或消息契约发布，不靠具体 Widget 或主角类互相强制转换。

### 3.4 状态所有权

个人档案和学习记录归服务器持有的 PlayerState/角色档案聚合；角色重生不丢失。身体姿态、当前移动与动作归 Pawn 及组件。菜单页签、光标焦点、搜索、详情弹层归 LocalPlayer UI，不复制给服务器。世界拾取物和 NPC 服务状态归世界实体/持久记录。

预览角色不是玩家 Pawn，不包含库存、ASC、AI 或反应模拟。推理 agent 属于一个视觉角色实例，不以玩家永久 ID 代替 Pawn 生命周期 ID。

### 3.5 架构验收

新增一个同机制物品、技能等级或普通 NPC 对话，不修改主角类、主菜单大 switch 或主线硬编码分支。关闭 UI 后服务器规则仍可独立测试。服务器目标不链接 Slate/UMG 或模型推理。单独更新 MotionBricks 库不要求修改库存和任务代码。

## 4. 数据、命令、事务与存档的统一契约

### 4.1 唯一数据来源

将现有规则 JSON 逐步迁移为按域拆分、显式 SchemaVersion 的规范源数据；策划展示资源由 ID 关联 `PrimaryDataAsset`，或者由同一规范源导出。必须选定每类字段的唯一权威来源。

推荐：玩法数值与条件来自按域 JSON/表格生成的数据注册表，图标、Mesh、Montage、音效等软引用来自配套资产。编译前/打包前校验两者 ID 和必要资源；不要让 JSON 和 DataAsset 分别编辑同一个攻击力。

展示名称使用本地化 `FText`/String Table，不把稳定 ID 当玩家名称。Gameplay Tags 表示分类、条件和状态；稳定实例 ID 与定义 ID 保持不同概念。

### 4.2 统一命令信封

所有会改变物品、装备、金币、学习点、任务奖励的操作具有：

```text
CommandId                 # 客户端生成的唯一请求 ID
CommandType               # 类型化动作，不使用任意字符串执行
ProtocolVersion
ActorIdentity              # 由服务器连接解析/绑定，不信任客户端自报身份
ExpectedProfileRevision
ExpectedWorldRevision?     # 只在涉及世界实体时使用
TargetStableId / ContainerId / ItemInstanceId / SkillId
Payload                    # 该动作允许的有限字段
```

结果包含 `CommandId`、结果码、最终版本、实际转移数量、受影响 ID、可读原因参数。服务器不得信任客户端价格、技能等级效果、距离、持有物品、前置条件或动作时间。

保留统一 `ProfileRevision` 作为跨域事务版本，先避免库存/技能分别提交导致不一致；页面刷新可以有独立通知序号，但不能误当数据库提交版本。重试同一命令保留同一个 ID 与完全相同载荷；改数量或目标必须生成新 ID。

### 4.3 原子事务与失败语义

执行顺序为：身份/限流 → 查回执 → 校验版本与条件 → 计算候选副本 → 验证全部不变量 → 原子发布持久化 → 发布新状态/复制/表现。

跨库存与世界拾取、跨技能与学习点、跨任务与奖励，均由一个事务协调者提交。不能各自保存一半。磁盘写失败、数据库冲突、服务器重启不得导致复制道具、重复奖励或扣点但没学到技能。

运行时 ASC、装备外观等由已提交记录幂等重建。需要跨崩溃恢复的一次性效果使用提交回执和可恢复投递记录，不将持久化成功与后续副作用之间的窗口忽略。

### 4.4 消耗品与崩溃窗口

消耗品扣除与效果应用必须定义清楚：治疗事务记录消耗结果及目标生命/资源状态版本，按提交后的结果恢复；或以唯一效果投递 ID 幂等执行并确认。不能仅在保存背包后调用一次 `SetVitals()`，然后把中间崩溃导致“药消失、效果没生效”当作正常。

同一会话战斗属性是否跨重连保留，由角色恢复策略统一决定；不能让背包服务擅自制定另一套复活规则。网络重复投递不会重复治疗或扣除。

### 4.5 回执与长期重试

现有最近 64 条成功回执的语义不等于永久回执保证。[G16] 完整实现应定义有界回执缓存、持久事务 ID 唯一性与旧请求过期规则。超过可重放窗口的旧请求只能拒绝并要求同步，不可重新执行。

使用单调版本及有界保存策略，防止恶意唯一 ID 请求无限增长。服务器不能靠客户端 UI 禁用来保证幂等。

### 4.6 资产与状态校验

编辑器、CI 和运行时加载都必须校验重复/空 ID、引用缺失、数量溢出、非法槽位、技能前置环、负成本、无图标、无动画、过大的数组、无效网络载荷。未知 major schema 拒绝加载，保留原存档并提示原因，禁止静默清空后保存。

新数据能够通过工具创建与验证；未知机制允许增加新的策略实现，但不允许为了每个新物品增写一个 `if (ItemId == ...)`。

<a id="ui-framework"></a>
## 5. 正式 UI 框架与视觉规范

### 5.1 确定采用的实现路线

采用 UMG + CommonUI 页面/弹层 + 事件驱动 ViewModel；不把正式布局继续写成一个巨大 C++ `RebuildWidget()`。CommonUI 基于 Slate/UMG 提供导航与输入组织能力；统一输入配置只由菜单框架管理，不与旧面板每帧 `SetInputMode` 并存。[U01]、[U02]

ViewModel 可以使用项目自有事件驱动 UObject；是否启用 UE MVVM 插件不改变契约，不作为整个功能交付的前提。选定实现后，同一页面不混用多种每帧绑定方式。

### 5.2 菜单结构

```text
WBP_PlayerMenu（可激活菜单）
  ├─ Header：角色名称、货币、关闭、设置入口
  ├─ TabBar：背包 / 技能 / 任务 / 地图 / 队伍
  ├─ PageStack / PageSwitcher
  ├─ ContextActionBar：当前设备的操作提示
  └─ ModalLayer：详情、数量选择、确认、错误恢复
```

`I/K/J/M/P` 直接进入对应页面；再次按当前页快捷键关闭菜单；按其他页快捷键只切换页。`Esc` 按详情子弹层→详情→菜单逐层返回；没有菜单时打开系统菜单。页面之间保留搜索、滚动和选中实例。

控制器肩键切页、方向键导航、确认键执行、返回键返回；详情提供与右键等价的控制器操作。输入设备切换立即更新图标，不抢走当前有效焦点。

### 5.3 视觉要求

基础素材只限定模型/美术来源，不允许用文字替代 UI 结构。界面必须有清晰的图标、格子、装备槽、技能节点、连接线、按钮状态、进度条和选中反馈。

以 1920×1080 为设计基准，采用统一间距、字体级别、边框和状态色；正文建议 18–22 px、重要标题 26–32 px、可点击格子建议 64–80 px，最终按 DPI/显示器和实测可读性调整。这些是设计目标，不是引擎限制。

必须适配 1280×720、1920×1080、2560×1440、3840×2160 和 21:9；不得靠每帧重新计算固定绝对坐标补救布局。长中文名称、不同语言文本、UI 缩放、窗口化与安全区均不能裁切关键信息。

状态不能只靠颜色区分：已装备有角标，可学习有形状/标记，锁定有锁标，错误有文字原因。获得焦点、悬停、选中、禁用、处理中、失败是不同状态。

### 5.4 数据与更新

打开页面时请求最新快照；随后订阅库存提交、装备变化、技能等级、任务进度与货币变化。销毁/换 Pawn 时解绑，重新绑定新上下文。不每帧重建全部 Widget，不每帧拼接全文，不以 Widget 是否 Tick 作为菜单能否再次打开的前提。

对异步图标与预览资源，校验当前 ItemId/请求版本，防止格子复用后迟到贴图出现在另一物品上。资源失败使用分类默认图标并记录错误；正式内容缺少必要图标仍不通过内容验收。

### 5.5 开关菜单时的行为

联机世界继续运行；打开菜单阻止本地移动、攻击、施法与世界右键操作，不暂停全局服务器。单人是否暂停由系统设置策略明确控制，不能让技能和世界时间使用不同暂停语义。

进入菜单统一终止输入层的冲刺/格挡保持状态，处理长按释放与重映射取消，防止关闭菜单后卡格挡或自动攻击。受击可提示并按既定策略关闭非关键页面，不能把“菜单打开”当服务器无敌状态。

### 5.6 UI 验收

从实际角色进入菜单、使用鼠标与控制器、重连、重生、切换分辨率后都能完成全部页面流程。控制台命令、开发按键和下拉商品 ID 不属于正式操作路径。

<a id="inventory"></a>
## 6. 背包、装备、拾取与商店的完整闭环

### 6.1 背包页面布局

左侧约 40% 用于角色预览及装备槽，右侧约 60% 用于分类、搜索、排序和物品格子；底部显示容量、货币和上下文操作。窄屏允许装备属性折叠，但不能隐藏主要操作。

默认保持现有 32 格容量语义，[G16] 在 1080p 可显示 8×4 格。列数可响应式调整，容量由定义决定，不能因为布局变成 6 列就改变可存物品数量。空格也必须显示。容量升级只通过正式规则修改，不由 UI 创建额外真实格子。

### 6.2 库存语义与固定格子

正式决定：**装备为库存实例的槽位引用，已装备物品仍计入背包容量并显示装备角标。**这与现有数据关系一致，避免迁移时改变归属。[G07] 因此满包也能卸下装备，卸下只是解除引用，不会再次创建物品。

引入独立 `SlotIndex`/格子位置映射。`InstanceId` 表示物品身份，`SlotIndex` 表示容器内位置，筛选后的 `ViewIndex` 仅表示显示位置，三者不可互换。

“全部”页支持保存的自由排列。分类和搜索页采用临时紧凑视图，不把拖到第 N 个筛选格误解释为真实第 N 槽：此状态下提供装备/使用/合并等目标明确的拖放，跨空格自由重排返回“全部”页操作。排序提供“仅当前显示排序”和“整理背包”两个不同动作；后者才提交真实槽位变更。

### 6.3 必须实现的操作

| 操作 | 完整规则 |
|---|---|
| 选中与详情 | 左键选中；右键打开固定详情；选择始终绑定 InstanceId |
| 使用 | 检查用途、数量、资源缺口、冷却及状态；扣除与效果有一致恢复策略 |
| 拆分 | 数量选择，源剩余正确，新堆新 ID，必须有目标空间 |
| 合并 | 校验 StackKey；可部分合并，回执返回实际数量，剩余留在源堆 |
| 移动/交换 | 空格移动保留 ID；两堆交换原子完成；合并与交换语义明确 |
| 装备/卸下 | 指定装备槽，完整校验占位与资格；属性与外观同步 |
| 丢弃 | 非任务锁定、非绑定限制、非已装备物；指定数量，服务器安全落点 |
| 拾取 | 距离、视线、归属、容量与领取事务；满包不销毁掉落 |
| 整理 | 确定性排序并可选择合并；处理中锁定冲突操作，失败还原显示 |
| 收藏/锁定 | 锁定阻止误售/误丢；与绑定、任务限制是不同规则 |
| 搜索/分类 | 支持名称与类别；清空条件恢复原选择或明确清除 |
| 快捷栏 | 存储实例或定义策略，不把屏幕格子下标作为快捷目标 |

拖拽只是触发同一个命令，不存在另一套“鼠标专用库存算法”。数量输入检查上下限与整数，不信任手工构造的超大/负数请求。

### 6.4 物品实例与堆叠

物品定义保存固定属性，实例保存数量、耐久、绑定、词条实例、归属和容器位置等运行状态。只有定义相同且影响交换语义的实例状态一致才允许堆叠。

`StackKey` 至少考虑 DefinitionId、品质/词条、绑定、任务实例约束和有意义的耐久/状态分组。堆叠行为不能洗掉装备磨损或让他人绑定物变成可售材料。

整件移动和丢弃/拾取保持实例身份；拆分新建 ID；合并消耗源堆时保留目标 ID，并记录发生的转换。装备实例不可被错误合并，数量恒为 1。

### 6.5 完整装备槽

默认角色配置开放以下槽位，并为每槽提供实际可取得装备：

```text
MainHand / OffHand
Head / Chest / Hands / Legs / Feet
Neck / Ring1 / Ring2
```

槽位来自角色装备布局定义，可用槽、允许标签、UI 位置和互斥关系均数据化。戒指可以放入任一允许戒指槽，因此将现有单一 `Slot` 验证升级为 `AllowedSlots` 与实例选定槽；保留旧定义的迁移映射。

双手装备占用主手并声明副手占位。装备双手武器时解除冲突副手引用；替换前必须在详情中明确变化。向被双手武器占用的副手拖盾，按规则显示“需先换为单手武器”，或以显式确认的原子组合命令处理，不能静默留下非法组合。

目前 `ValidateLoadout` 中的数量上限与 `Rule->Slot == Pair.Key` 等假设须一起重构，不能只在 UI 中新增槽位。[G08]

### 6.6 属性、耐久与修理

装备影响由统一属性计算器/GAS GameplayEffect 适配执行。装备变化先提交合法 loadout，再移除旧来源效果、应用新来源效果，按来源句柄保证不叠加泄漏。升级、卸下、重生、重连均幂等重建。

正式支持武器伤害/架势/动作配置、防具防御/抗性、饰品资源或能力修饰；不开放没有实际结算作用的属性行。生命上限下降时对当前生命的处理统一为夹取，不额外治疗；消耗和减免有上下限。

耐久仅对启用耐久规则的装备生效，必须同时交付磨损来源、低耐久提示、损坏后效果、存档、修理入口及花费事务。至少包含一件可磨损装备的完整演示；禁用耐久的装备不显示假的耐久条。用户锁定、任务限制和耐久状态在出售/丢弃中共同检查。

装备对世界材料反应的影响只通过明确的属性/能力适配传递，不能直接修改反应求解器的内部数组。

### 6.7 外观完整性

主副手必须使用正确 Socket 与 GripTransform，支持单手、双手、盾与施法器姿态。防具可以用 UE 基础几何体或模块化基础网格，必须随身体运动且不明显穿透。不可见的小饰品允许只提供真实属性、图标与槽位，不强制放大成世界几何体。

装备视觉加载失败不会回滚已确认归属，但必须显示可识别兼容视觉并记录告警；发布内容中所有必要 Mesh/Socket 引用须通过校验。

### 6.8 世界掉落、容器与拾取

区分“场景中可搬运的物理物件”与“能进入背包的道具实例”。拾取接口读取 `InventoryPickup` 能力，不把所有带 Mesh 的对象装进背包。

掉落保存稳定 ID、完整实例状态、数量、归属策略、持久位置与领取版本。普通整件拾取维持 ID，部分拾取创建明确的拆分记录；满包允许按规则拾取可容纳部分，并说明剩余数量。

默认共享掉落沿用服务器先到先得，任务奖励为个人领取。队伍归属策略可由定义选择，但本版本不新增骰子分配等未实现入口。并发领取必须只有一次成功；落地位置不合法、区域未就绪或存储失败时不从背包扣除。

个人仓储与普通战利品容器共用容器契约，支持容量、页签和两栏转移，跨容器转移原子完成。明确源/目标容器权限，不能由客户端传别人的 ContainerId 读取或移动道具。

世界中的燃烧、高温危险物件如不具备安全收纳规则则禁止入包并给出原因；收纳后不在背包内继续运行一套隐形世界求解器。需要保留湿润、冻结等物品状态时，按该定义的收纳状态策略保存与恢复，不能靠入包清除关键负面状态。

### 6.9 商店与修理

与商人交谈后打开正式交易界面，显示该商人的商品而不是所有商店商品并集。数量、单价、合价、拥有数量、库存与购买条件可见；价格由服务器定义和购买时状态决定。

出售可看到卖价、不可出售原因、锁定状态和已装备标记；有确认机制。修理显示当前/修复耐久和费用。离开交互范围、商人被卸载/失效、发生战斗限制时，会话失效，未提交交易不执行。

商店有限库存、个人购买限制只在已配置时出现；没有实现有限库存的商人不要显示虚假余量。回购如果提供入口就必须实现事务和保存，否则本版本不出现该入口。

### 6.10 背包工作包完成条件

实际完成“拾取 → 拆分 → 拖动 → 装备 → 属性改变 → 角色预览同步 → 出售/修理 → 丢弃再拾取 → 重连/读档恢复”。必须包含满包、双手冲突、被锁物品、相同道具不同实例状态、并发领取与存储失败场景。

<a id="inspection"></a>
## 7. 角色预览与统一右键详情系统

### 7.1 角色预览实现

采用独立本地预览 Actor、专用 SceneCapture2D、RenderTarget 与 UI 材质。预览只订阅角色外观和已装备展示快照，不复制真实 Pawn，不参与世界服务。捕获白名单只含预览对象与必要灯光；预览舞台不能被世界玩家看到，也不能靠放到极远世界坐标而触发区域流送。

预览显示完整角色、装备和待机；可旋转、有限缩放、重置视角。鼠标拖动预览只影响预览相机，不改变实际玩家朝向。换装备仅更新改变的部分；资产加载完成时核对当前展示版本，避免迟到结果覆盖新装备。

菜单关闭后停止捕获和非必要 Tick；根据缓存预算保留或释放 RenderTarget。渲染透明背景时必须检验捕获源与 UI 材质 alpha，在发布包中确认不是黑底、全透明或丢失抗锯齿。

### 7.2 预览和真实角色共用展示配置

使用相同角色外观解析器、Socket/GripTransform 与装备网格定义，但不共用 Gameplay Component 实例。预览所需动画由独立展示状态选择，不能读取真实角色的“被击倒”状态导致背包无法观察装备。

至少在 Manny、Quinn 或项目实际使用的两套人物体型上验证握持、护甲与脚底站位。预览不得默认遮挡头部、脚部或双手武器末端。

### 7.3 统一 Inspect 对象

```text
InspectTarget = ItemInstance / ItemDefinition / EquipmentSlot / SkillNode / StatusEffect
InspectContext = OwnerIdentity + SnapshotRevision + OptionalComparisonTarget
```

详情由统一 `InspectionService` 构建只读数据模型；实例信息取已授权快照，基础说明取定义，装备比较取与真实装备相同的属性计算器。详情页不会自行估算一套与战斗不同的伤害。

### 7.4 三种不同的信息层

悬停摘要为短暂、不可交互的 Tooltip；右键详情为可停留、可滚动、带操作按钮的弹层；数量/危险确认是详情上层子弹窗。三者不要混用一个自动消失的 Tooltip。

| 对象 | 必须显示 |
|---|---|
| 道具 | 图标、名称、类别、数量、用途、冷却、使用限制、可交易状态 |
| 装备 | 槽位、品质、属性、耐久（适用时）、需求、来源、比较差异、双手冲突 |
| 技能 | 等级、实际效果、消耗、冷却/施法限制、前置、学习成本、下一级效果 |
| 锁定技能 | 锁定原因和可追踪前置；查看不等于学习 |
| 状态效果 | 效果来源、剩余时间、影响；没有持续时间的效果不伪造倒计时 |

右键本身不装备、不学习、不消耗。弹层内动作均路由到同一命令服务。点击空白或 Esc 关闭，鼠标位置接近边缘自动翻转/夹取；窗口缩放后重新布局。对象已被使用/出售/合并时显示“对象已变化”或关闭操作，不落到相邻物品。

### 7.5 装备比较

支持与指定可替换槽比较；戒指显示选择 Ring1/Ring2，双手武器比较包含被卸下的副手。增减用数值、正负符号和辅助颜色共同表达；未知属性不显示 0 冒充真实数据。比较是只读模拟，不把预览装备写入真实 loadout。

<a id="skills"></a>
## 8. 技能树、学习、升级与 GAS 重构

### 8.1 功能边界

完整交付可查看、可学习、可升级、可装备到快捷栏、可释放、可存档、可迁移、可联机的技能成长系统。第一套内容以现有四种元素技能为基础，每系三级线性成长；系统支持分支和合流的有向无环前置关系，但不以无限内容数量作为完成条件。

```text
引焰 I ── 引焰 II ── 引焰 III
引泉 I ── 引泉 II ── 引泉 III
霜凝 I ── 霜凝 II ── 霜凝 III
雷击 I ── 雷击 II ── 雷击 III
```

界面必须用真实图标节点、连线、层级和状态展示这些路线，不允许把以上文字图原样放进一个 TextBlock 当最终技能树。

### 8.2 身份分离与 GAS 映射

现有实现将技能编号隐含在 AbilityLevel 中，[G10] 必须替换为：

```text
SkillId / AbilityDefinitionId    # 稳定技能身份
ElementTag                      # 元素或机制分类
LearnedRank                     # 当前学习等级
AbilitySpecHandle               # 当前 ASC 实例的运行句柄，不写永久存档
InputSlotId                     # 玩家快捷栏映射
GrantSourceId                   # 学习、装备或临时效果的授权来源
```

可采用共享数据驱动 GA + 每个 Spec 的定义来源，或有限的机制 GA 派生类；同类多技能不能按 `FindAbilitySpecFromClass()` 取第一个来代替身份查找。`AbilityLevel` 只表达等级，不再用于选择火/水/冰/电。

永久学习、装备授予和临时授予分别记账；卸下装备只移除该来源授予，不删除已学技能。重生时 ASC Avatar 重绑后重建授权，不重复叠加被动。

### 8.3 定义与成长记录

技能定义包括名称/图标/说明、机制定义、各级效果、前置要求、技能点成本、任务/等级条件、目标类型、施法资源、冷却、动画与特效引用。树布局独立于前置规则，拖动节点编辑位置不会改变学习条件。

个人记录包括 LearnedRanks、AvailableSkillPoints、已获得点数账本、学习事务记录、快捷栏配置及不可退还的故事授予。用 SkillId 保存，不保存 UI 节点数组位置或运行 SpecHandle。

等级点数来源必须实际接通：升级、任务奖励等由唯一事件 ID 授予；每条来源只发放一次。禁止仅在测试初始化里添加 999 点，让普通玩家没有获得路径。

### 8.4 主线必需能力不制造死锁

基础引焰/引泉按既有训练流程作为故事授予或零成本必得节点，导师对话能完成授予并引导训练。霜凝/雷击遵循迁移后的故事门槛。用于通过主线必经目标的基础能力不得因自由加点耗尽而永久缺失。

高级技能通过点数/条件解锁。技能详情能够定位前置技能，或把前置任务设置为追踪目标。满足任务条件不代表自动扣点学习高级技能，必须有明确学习确认。

### 8.5 学习与升级事务

点击节点选中 → 展示当前/下级收益和成本 → 点击学习/升级 → 服务器复验当前等级、前置、点数和状态 → 同时扣点并写学习记录 → 提交成功 → 授予/更新 GA 与效果 → 回执、动画和 UI 更新。

处理中节点显示待确认，不立刻把树永久点亮。重复请求、快速双击、重连重试、冲突版本均不得重复扣点；失败不改变效果。技能版本更新后重新校验定义映射和已学等级。

### 8.6 真正改变玩法参数

四系升级必须至少改变一项可测且在界面中准确描述的能力参数，如作用范围、命中传递量、持续方式、施法资源或冷却效率。不能只更新名称和一行等级。

仍遵守少数通用规则：火提供热/点燃条件，水转移有限水资源，霜凝抽取热量并由材料决定冻结，电提供受规则约束的电刺激。升级不得绕开距离、材料响应、归属、服务器检查和资源守恒。尤其不能把“水量增加”做成只增加输出而不增加消耗或供水条件。

UI 数值由同一等级参数解析结果生成；“下一级预览”和服务器实际效果必须有一致性测试。

### 8.7 技能页面交互

节点状态包括未开放、缺少前置、资源不足、可学习、已学习可升级、满级与处理中。每个状态都有图标/样式和原因，不只变灰。

支持鼠标点击/右键、控制器沿前置链移动、路线选择、缩放和平移（内容超出视口时）；不能要求玩家拖动很远才能找到当前节点。技能点显示始终可见，右侧显示详情和学习按钮，底部是快捷技能栏。

快捷位只绑定已授权主动技能；被动技能不可拖入施法栏。暂时失去装备授予时保留可识别失效位并禁用，重新授权后恢复；永久删除/迁移时明确提示。

### 8.8 重置与退款

交付受规则限制的重置入口：安全地点/导师服务、预览受影响节点、退款规则和确认。故事基础授予不能被重置掉。重置一个前置时，其依赖节点按拓扑顺序一并撤回，使用实际花费账本退款，不能按新价格套利。

正在施法、冷却中或战斗中不允许通过重置绕过限制。撤回的技能从 ASC、被动效果与快捷栏正确处理。重置与点数变更同一事务。

### 8.9 旧法术迁移

旧位 0/1/2/3 映射到引焰/引泉/霜凝/雷击 I；保留历史学习，不重复领取故事奖励。仅知道已学不能推定旧玩家支付过点数，因此按旧故事授予来源迁移，不虚构退款账本。

同时替换 `LearnedSpells` 的验证上限、旧代码位运算、教程判断和旧 NetSerialize 依赖。兼容读取完成并生成经过验证的新存档前，不删除旧结构解码路径。[G09]、[G15]

<a id="interaction"></a>
## 9. NPC、对话、任务与世界交互

### 9.1 交互候选的统一契约

设计无副作用查询 `QueryInteractionOffers(Context)`，返回动作列表而不是单个“能否交互”布尔值：

```text
TargetStableId + ActionId + InteractionRevision
DisplayVerb + Icon + Priority
Availability = Hidden / TalkOnly / Available / DisabledWithReason
ReasonCode + ReasonParameters
DialogueNodeId? + QuestId? + ObjectiveId? + ServiceId?
```

客户端基于复制数据计算提示；服务器使用同一规则定义并重新检查。客户端无法知道的秘密条件不得提前泄露；服务器拒绝时返回可公开原因。查询不能发奖、生成训练目标、点亮任务或消耗资源。

### 9.2 提示规则

| 对象状态 | 显示与行为 |
|---|---|
| 纯背景人物，无对话/功能 | 不显示交互图标和按键 |
| 有对话但无新任务 | 显示“交谈”，提供符合角色和进度的对话 |
| 服务当前可用 | 显示具体动作：交易、训练、休息、领取等 |
| 服务尚未开放但可沟通 | 显示“询问/交谈”，解释原因并提供主线目标入口 |
| 临时忙碌、受威胁、倒地 | 根据定义隐藏或显示真实状态，不显示普通交易提示 |
| 可烧、可冻、可搬但不响应 E 的对象 | 显示对应物理/操作提示，不伪造 E 交互 |
| 已拾取/已领取的个人对象 | 不再提示同一领取动作；仍存在其他动作时只显示那些动作 |

同一个 NPC 不需要“永远有新任务”才能交谈；也不应将“不能购买”误当“这个人不能沟通”。

### 9.3 候选选择和目标一致性

范围检测收集候选，按屏幕/视角中心、距离、动作优先级与遮挡选择，增加焦点迟滞避免轻微移动时提示闪烁。只查询附近已注册对象，不每帧扫描全世界所有 Actor。

按 E 时提交当前目标 ID 与动作 ID。服务器验证这个目标，不重新选择另一个最近 NPC。目标改变、卸载、遮挡或任务版本变化时返回目标失效/条件变化，更新提示；不能转而执行旁边箱子的动作。

长按救援等操作具有开始、进度、取消、完成状态，进度反馈来自同一动作实例；受击、距离、目标复活或断线都可正确取消并释放占用。

### 9.4 对话数据与服务处理器

对话定义包含人物身份、发言文本、选项、公开条件、下一节点、允许的类型化动作和结束行为。NPC 挂载对话/交互配置，服务由 `IInteractionHandler` 注册处理，任务状态通过查询接口获取。

对话动作只允许有限命令，例如进入商店、请求训练授予、追踪目标、提交任务；不得在资源中存任意脚本字符串直接执行。日常闲聊与主线条件分开，避免给每个路人硬编码一整条任务链。

UI 显示头像/人物名、正文、选项与返回，支持键鼠/控制器。文字本身是对话内容，不需要用图像替代；但对话框必须是真实可操作 UI，而不是屏幕角落的调试输出。

### 9.5 主线引导闭环

导师发现前置未完成时，根据当前玩家进度定位第一个未完成且可行动的目标。例如未登记则指向登记台；已经登记但未绑定据点则指向旅舍；完成前置则显示学习/训练入口。

选项“追踪这个目标”调用任务目标解析器，更新任务追踪、地图标记与世界方向提示；不会直接把任务置为完成。目标 Actor 未加载时使用持久锚点位置，加载后再绑定当前实例。

完成主线后不返回“没有新目标，按 J”作为全部对话；导师提供训练/技能重置，商人继续交易，普通人物有合理结束语。当前个人状态与全局世界状态分别判断，玩家 A 的进度不能覆盖玩家 B。

### 9.6 既有服务的迁移覆盖

登记、旅舍、导师、商店、招募、个人训练、日常委托、井/水桶、门/泵/电源、采集、共享掉落、救援、修道院与中继活动，必须逐一迁移到处理器或明确保留的通用机制入口。不能只修导师，其他服务留在巨型分支中。[G12]

### 9.7 交互验收

检查无对话背景人物、可聊不可交易人物、多个重叠目标、被墙遮挡、已完成任务、不同玩家不同进度、交互中目标卸载、重复点击和断线。每一次提示的动作必须与实际执行的目标/动作一致。

## 10. 输入、移动、战斗与动作规则

### 10.1 输入配置

正式默认键位：空格跳跃，左 Ctrl 下蹲/起身，左 Alt 闪避，左 Shift 冲刺。保留现有 C 投掷、Q 药品、E 交互等操作的明确映射，避免简单换键引入另一组冲突。[G13]

使用资产化 Enhanced Input Actions/Mapping Context，按 Gameplay、Menu、Dialogue、Rebind 等上下文管理；控制器提供完整映射。用户设置支持重映射、冲突提示、恢复默认、下蹲保持/切换、镜头灵敏度与反转。

不能在启用 CommonUI 后仍由多个 Widget 调用输入模式接口。打开菜单时释放保持输入；窗口失焦、手柄断开与重映射取消同样清理状态。

### 10.2 单一权威移动源

继续以 CharacterMovement 为移动、碰撞和网络预测基础。普通移动、跳跃、重力、地面/坡面/移动平台由它控制。MotionBricks 输出姿态和候选运动信息，不直接以 `SetActorLocation` 推着玩家穿过世界。

角色朝向区分探索模式的运动朝向与战斗锁定/侧移朝向；目标速度、最大速度、加速、制动、旋转速度、冲刺消耗和下蹲速度统一来自移动配置，不能由多个 Tick 互相覆盖。

### 10.3 基础动作状态与组合约束

至少支持：站立待机、走、跑、冲刺、启停、转向、战斗侧移、跳跃起跳/上升/下落/落地、下蹲进入/移动/退出、地面闪避、轻重攻击、格挡/招架、施法、受击、眩晕、倒地/死亡、复活、拾取、搬运/放下/投掷。

状态不宜用一个巨大枚举覆盖所有组合。分离移动模式、姿态、装备姿态、动作实例和受限标签；规则表决定哪些可以并行、覆盖或取消。例如冲刺与下蹲互斥，倒地覆盖全部自主动作，搬运大物件禁止某些武器动作。

优先级示例：死亡/倒地 > 强制受击/眩晕 > 已提交特殊动作 > 战斗动作 > 普通移动。实际允许的取消窗口数据化，不能简单让优先级高的动作随意免除已支付成本。

### 10.4 跳跃

空格只触发一个跳跃入口，Completed/Canceled 正确结束保持。允许单一跳跃的短按/长按高度差，但不能存在“空格是假跳、Ctrl 才真跳”的重复映射。

校验站姿、地面、动作限制与资源；落地时根据实际下降速度选择轻重落地，不按播放动画是否结束决定角色落地。不得在动画通知中再次添加跳跃冲量。

### 10.5 下蹲

通过 `Crouch()/UnCrouch()` 和 CharacterMovement 的胶囊空间检查处理真实碰撞高度，而非缩放模型。下蹲速度、镜头高度过渡与动画姿态同步，头顶有障碍时保持下蹲，不能穿顶起身。[U03]

默认下蹲时按跳跃先请求起身；只有空间允许且跳跃规则满足才起跳。冲刺取消下蹲也必须经过起身空间检查。服务端与远端同步真实姿态，不以客户端镜头高度推断姿态。

### 10.6 地面闪避

当前 `LaunchCharacter` 路径会进入 falling，[U04] 不能只把 Z 从 80 改为 0 就宣告修复。

采用专门的地面 Dodge 动作：固定服务器规则定义距离/时长/速度曲线和体力、通过 CharacterMovement 的受碰撞位移或 RootMotionSource/自定义移动实现，独立播放翻滚或侧步动画。网络预测、取消与服务器纠正必须共同实现。[U05]

平地闪避应保持地面贴合，遇墙减速/停止，不穿墙；冲出平台边缘后自然进入 falling，这是正常物理而不是强行保持在空中。禁止空气中无限闪避，除非以后明确增加空中闪避能力并完整实现。

无敌窗口、冷却和体力由动作规则/GA 控制，不取决于生成模型恰好播放到哪一帧。响应失败时客户端预测要回滚。

### 10.7 战斗与动画的权责

GAS 负责授予、成本、冷却与可取消能力；Combat/ActionRuntime 负责动作阶段、命中窗口和状态；Equipment 负责当前武器定义与展示；Animation 负责表现。不能再由两个模块分别扣体力或重复开启命中。

攻击时间线包含前摇、生效、恢复与允许取消区间，连击序号与输入缓冲有明确规则。服务器按动作实例及目标去重命中。武器碰撞/命中取受控动作轨迹或经过权威计算的碰撞体，不依赖仅客户端生成、服务器不存在的随机手部骨骼位置。

Montage Notify 可驱动音效和视觉，也可作为权威动作时间线的受控信号，但不是唯一伤害时钟。专服不播放 Mesh 动画时，仍能正确结算攻击、格挡和技能。

### 10.8 特殊世界动作

拾取、搬运、放下、投掷和救援必须有完整姿态、手部接触和取消，不能只有物品瞬移到角色前方。动作开始先校验目标和可达位置，提交点后处理物品状态，取消/受击/断线释放手部约束和物体占用。

现有过桥、承重冰面、移动物体和融冰过程继续接受真实碰撞与移动基座规则，不能为动作表现绕开这些机制。需要越障时使用明确高度、厚度、落点和净空检测的 Vault/Mantle 动作；本方案将低障碍翻越纳入正式动作内容，不承诺任意墙面自由攀爬。

### 10.9 动作完成条件

所有动作在实际地图、带装备、带碰撞、单人与远端联机状态下运行，并且都有可用资源和规则。不能用跳跃片段表示眩晕、用抬手骨骼旋转表示全部格挡、或用静止姿势替代下蹲移动后宣称完成。

## 11. motion-bricks.cpp 的正式 UE 原生集成

### 11.1 最终集成方式

**使用原生 C ABI 动态库直接嵌入 UE 客户端，不以 Python、Go、浏览器、WebSocket 或本机 HTTP 服务作为正式动作运行依赖。**这些上游示例不是库的必要运行组成。[M03]

通过独立 CMake 构建 C++23 原生库，通过 UE External Module/运行时模块加载。不要为了接库把整个游戏 C++ 标准强行改为 23；C ABI 隔离编译器对象布局、异常和 STL 边界。UE 模块只包含固定宽度类型、指针和 opaque handle 的上游 C 头文件。[M03]、[M05]、[U06]

原生组件目录、构建版本、模型版本和风格资产都纳入发布清单。包中存在完整传统动画与正式生成动作路径；默认后端由已验证硬件配置及运行时可用性决定。

### 11.2 插件组成与职责

| 组件 | 完整职责 |
|---|---|
| `MotionBricksNative` | External Build.cs、固定头文件、库文件与依赖部署清单 |
| `FMotionBricksApi` | 安全加载库、解析必需符号、状态码/错误转译、ABI/版本检查 |
| `FMotionBricksModelOwner` | 模型、options、styles 的 RAII 生命周期与引用约束 |
| `FMotionBricksScheduler` | 唯一模型访问线程、任务合并、预算、优先级、结果发布 |
| `UAetherMotionComponent` | 当前角色的注册/注销、输入快照、角色 epoch 与 provider 状态 |
| `FAnimNode_AetherGeneratedPose` | 读取已完成的不可变姿态缓存，输出源骨架姿态，不做推理 |
| `UAetherMotionProfile` | 风格/动作适用范围、骨架、重定向、时间与质量参数 |
| `AetherMotionEditor` | AnimGraph 编辑器节点、风格导入/烘焙、模型/骨架校验及预览 |

这些是项目拟新增组件名，并非上游已提供 UE 类。`AetherMotionRuntime` 对游戏业务保持无知；游戏动作适配器负责将 Gameplay 状态转为通用运动输入。

### 11.3 固定依赖与可重复构建

固定原生仓库提交、GGML 子模块提交及必要补丁、CMake 参数、编译器/运行库、模型及风格哈希，不能构建时自动跟随 `main`。以 `ee0cf5d...` 为本次起点，升级必须重新跑兼容矩阵。[M02]

构建配置至少包含：

```text
MOTIONBRICKS_ENABLE_GGML=ON
MOTIONBRICKS_ENABLE_PHYSICS=OFF
MOTIONBRICKS_DOWNLOAD_MODELS=OFF   # UE/正式构建不隐式联网；模型在受控资源步骤准备
MOTIONBRICKS_CPU_ALL_VARIANTS=ON   # 按目标平台校验并部署实际生成的 CPU 后端
MOTIONBRICKS_ENABLE_VULKAN=ON/OFF  # 分别产生并验证支持矩阵
```

以上选项来自已核查 CMake。[M05] 不能用 `ENABLE_GGML=OFF` 的非神经 ABI 子集通过冒烟后宣称真实推理接入完成。

构建与资源准备解耦：模型由显式下载/校验脚本或制品库获取，正式游戏安装包中已经包含已选模型与所需风格，正常启动不联网、不下载随机文件。不把 Python 转换工具带成玩家必须安装的环境。

Windows 核查 DLL、import lib/static lib 名称及依赖，固定运行库策略。上游 Windows 提交解决了静态库与导入库同名冲突；不要复制该提交以前的构建脚本。[M02]

### 11.4 UE 加载、打包与后端搜索

采用受控绝对目录加载，校验必需 `mb_*` 符号。ABI 1 不保证每个二进制都有全部新增函数，因此记录 `NativeRevision + RequiredSymbolSet`。禁止从当前工作目录、任意 PATH 或玩家可写搜索目录加载未校验库。[M03]

除主 DLL 外，部署 GGML core/base、CPU 变体和启用的 Vulkan 后端及其实际传递依赖。后端目录在第一次模型加载前统一设置；上游说明已加载后端在进程中共享，因此多 PIE/多世界必须共用一致初始化。[M07]

UE 的 RuntimeDependencies 用于 Stage 原生文件；原生库通常读取操作系统文件，DLL 也由系统加载，不能仅放入 PAK/IoStore 后假设原生 loader 能找到。模型与 `.mbstyle` 采用受校验的 loose NonUFS 数据包，或由项目实现完整、原子、安全的释放到只读缓存流程后再交给库。首选前者，避免不必要的启动复制。[U06]

插件二进制和模型是构建制品，通过固定配方与制品发布进入 Stage；遵守仓库不提交项目生成 `Binaries/Intermediate/Saved` 的约定。记录许可证和依赖哈希，不把第三方大文件随意塞入普通 Git 历史。[G17]

### 11.5 模型、风格与资源生命周期

正式模型 bundle 包含 `manifest.json`、`pose.gguf`、`root.gguf`、`vq-decoder.gguf`、`support.gguf`；风格使用 `.mbstyle`。支持的 G1 拓扑、版本、参数角色与数值由上游严格校验。[M06]

README 所述约 0.73 GB 是发布 F32 资源体积描述，不等于运行时内存/显存占用。[M01] 必须实际测量权重、计算图、临时 buffer、GGML 后端和 UE/驱动合计开销。不假定已有 Q4/Q8 量化支持；任何量化优化都必须新增格式支持并重新做质量/性能验收。

进程级 native service 统一持有模型与队列；世界/角色持有轻量会话。默认共享一个模型，不给每个角色重复加载。需要多个独立推理 worker 时只能使用独立模型句柄，并说明额外内存成本；不擅自共享一个句柄并发推理。[M03]

model 必须长于 agent；command 借用 style，style 不能在 agent/command 使用中释放；motion 输出独立持有但 getter 返回借用数组，释放 motion 前必须复制到 UE 自有缓存。[M03]、[M07]

退出顺序：停止接收任务 → 标记会话失效 → 等待在途调用正常结束 → 释放 command/agent/style → 释放 model/options → 确认无函数调用后卸载库。PIE 结束、地图切换与插件热重载执行同样约束。原生后端涉及进程级状态时优先维持到进程退出，不强行热卸载。

### 11.6 选择正确 API，保留控制权

**持续移动使用有状态 agent：**共享加载模型；加载匹配风格；每个视觉角色创建 agent；reset 或提供至少四帧 G1 context；设置方向、朝向、速度、风格和种子；调用 `mb_agent_plan`；按实际播放帧推进 `mb_agent_advance`。[M03]、[M07]

**明确起止姿态的动作衔接使用无状态 inference：**项目提供同一 canonical frame 下各四帧 source/target G1 姿态，设置允许时长、种子与必要 mask，调用 `mb_model_infer`；项目负责世界还原、重叠剔除、接缝融合和播放调度。无状态只是不保存动作控制状态，并不意味着模型可跨线程并发。[M04]

本版本不引入 MuJoCo/SONIC 替代 UE 物理。保留 `ENABLE_PHYSICS=OFF`，不调用 `mb_physics_*` 或 `mb_sonic_*`。这些能力不是角色动作生成的必需依赖，避免两个物理世界互相争夺角色控制。[M03]

### 11.7 非阻塞线程与队列

游戏线程只采集 POD 输入快照和消费已完成输出；AnimGraph 只读取不可变姿态缓存；推理在独立调度线程完成。任何帧内路径不得等待模型加载、GGUF IO、完整推理或 GPU fence 结束。

同一 model 的 plan/infer、agent context/advance、style 变更等操作统一串行。队列每个 agent 最多保留一个执行中请求和一个最新待处理请求，连续输入合并覆盖旧待处理值。批次内 agent 唯一，数量不超过上游界限；不把“支持 64 请求”写成“64 个角色一定能同时实时”。[M03]

优先级：本地玩家 > 镜头内近处队友/关键 NPC > 其他可见角色。长时间不可见角色降级，不为了保持 generator 活跃浪费预算。队列长度与峰值内存有明确上限。

线程池与 GGML 内部线程不能同时无限扩张。默认线程配置由目标硬件性能档案决定；CPU 与 Vulkan 后端都测量并记录竞争渲染后的实际表现。

### 11.8 请求与结果版本

每个请求至少包含：

```text
WorldEpoch / PawnEpoch / AgentGeneration / RequestSequence
MovementRevision / ActionInstanceId / MotionProfileRevision
SimulationTime / ConsumedFrameIndex / NativeModelRevision
```

死亡、重生、传送、切地图、切后端、姿态突变、主动动作覆盖都增加相应 epoch。迟到结果在发布前检查这些字段，不允许旧走路结果覆盖新下蹲或新 Pawn。

上游 agent 可能已在 plan 后改变内部状态；仅丢弃 UE 输出不足以保证下一次 context 正确。结果不采用时，调度器必须用最后接受并消费的上下文重新同步/重建 agent，不能继续推进未播放的旧计划。

### 11.9 时间、重规划与低延迟

模型输出为 30 FPS，而游戏可为 30/60/120 FPS。播放缓存用时间插值：位置线性或受约束插值、四元数正规化后球面插值，循环/边界保持连续。[M03]

`advance` 只推进实际已经消费的整帧数量，保留小数帧余量；不能每个 Tick 将 `DeltaSeconds * 30` 取整导致 60 FPS 下永远推进 0 帧。慢帧、菜单暂停、时间膨胀和网络时间纠正都有独立测试。

下一次 plan 在缓冲耗尽前根据估计耗时与输入变化触发，不能等待整个 24–64 帧片段播完才响应反向输入。发生急停、跳跃/下蹲、格挡或受击时，游戏规则立即生效，必要时立即融合至兼容动画，待新结果有效后再平滑进入生成动作。[M04]

不会通过多等一秒生成完整片段来换取“平均很流畅”。评价包括输入到表现延迟、帧间停顿和缓冲不足率，不只有每秒生成帧数。

### 11.10 生成根运动与真实移动的关系

普通移动由 CharacterMovement 控制胶囊。MotionBricks 的根轨迹用于姿态预测、步幅/转向与相位调整；全局根位移不重复叠加到 Actor。脚底接触、视觉 pelvis 高度与胶囊底部有明确偏移，不将 G1 root 直接当人物胶囊中心。

每次重规划使用当前权威/预测后的实际位置、朝向与已消费姿态重新锚定。撞墙、移动平台、坡面、速度被限制或服务器纠正后，丢弃/重建不再匹配的上下文，防止身体继续前进、脚滑和根骨飘移。

特殊位移动作由受控 RootMotionSource/CharacterMovement 动作处理，生成结果仅辅助姿态。需要手接触门把、拾起物体或翻越落点时，位置净空、路径碰撞和目标接触由 UE 校验与 IK/受控动画保证。上游边界条件不是刚性 pose pin，也不保证物理可行性。[M04]、[U05]

### 11.11 骨架与坐标适配

建立源骨架 `SK_G1MotionSource`（名称为项目目标资产），从上游 API 读取关节名称、父层级和中立位置构建/校验，不凭名称相似直接填 Manny 骨骼数组。G1Skeleton34 与任意 humanoid、SMPL-X、SOMA 都不等同。[M03]、[M07]

坐标适配在资源导入时标定并固化一个正交基变换 B：米到厘米只用于平移；旋转通过 `R_UE = B · R_MB · B⁻¹` 转换后重新形成并正规化四元数。必须处理左右手系、Y-up/Z-up、前方向和骨骼参考朝向，不能随意交换 quaternion 的 x/y/z 即认为正确。

导入器使用朝前、向右、上升、原地左右转的已知夹具确定轴向；发布前验证 round-trip 与脚部落地。额外人物脊柱、twist、手指和面部骨骼由目标参考姿态、握持 Pose 和 IK 处理，不宣称 G1 生成模型已经产生细致人手动作。

### 11.12 UE 动画图与重定向

正式路线为：源骨架姿态组件/AnimNode → Runtime IK Retargeter → 人物动画层 → 装备上身/全身动作融合 → 手脚 IK → 输出。源姿态组件不可见但按需更新；确保源先于目标，不能因隐藏 Mesh 被引擎优化而停更。UE 提供运行时 Retarget Pose From Mesh 路径，可用于跨骨架姿态转移；资产与参考姿态仍需项目制作和校验。[U07]

游戏线程将完成数据交换给 AnimInstance Proxy，任意线程动画评估不访问可变 UObject、不调用原生推理、不释放 native handle。给内存读写建立明确生产/消费边界，使用双缓冲/三缓冲或不可变引用快照。

不要每帧在游戏线程遍历修改真实 SkeletalMesh 的全部骨骼后又让 AnimGraph 覆盖，也不使用单个 PoseableMesh 绕过正式角色动画、LOD 和装备附着。

### 11.13 动作适用矩阵

| 行为 | 生成动作责任 | 必须保留的受控责任 |
|---|---|---|
| 探索走跑、启停、转向 | 正式生成基础姿态与风格变化 | CMC 位移、碰撞、速度限制 |
| 蹲走、战斗侧移 | 经验证的风格/边界驱动 | 下蹲胶囊、朝向、手持姿态 |
| 跳跃/落地衔接 | 经验证后用于姿态与过渡 | 起跳冲量、重力、落地判定 |
| 攻击、格挡、施法 | 可用于进入/离开动作的衔接 | 受控 Montage/动作层、成本、命中与取消窗口 |
| 拾取、搬运、翻越 | 可生成非关键过渡 | 可达检测、接触目标、物品提交、路径安全 |
| 死亡、复活、强制受击 | 不要求模型自由生成 | 可靠的受控动画与状态恢复 |

以上矩阵不是“未接入的功能留以后”。所有行为都必须完整可用；生成与受控动画的混合本身就是正式设计。生成部分的完成证明必须包含实际输入变化引起的新推理结果，不是预烘焙片段冒充。

### 11.14 故障、超时与兼容路径

后端策略为经测试的自动选择，也允许设置为 CPU/Vulkan/传统动画。模型缺失、校验失败、Vulkan 不可用、推理返回错误或输入过期时，在不改变游戏规则的前提下切换传统动作并呈现可诊断状态。

CPU 仅在实测满足预算时作为生成动作后备，不能自动切 CPU 后阻塞主线程。传统动画覆盖全部基础动作，切换时通过相位/姿态融合避免 T-pose；恢复生成需要稳定通过一段有效结果，不每帧来回跳。

**超时不等于原生调用已取消。**已核查头文件没有给出可据此假定安全抢占的取消契约。[M07] 超时采用逻辑废弃结果、停发新请求和视觉降级；在途线程正常返回前不释放模型、不强杀线程、不卸载 DLL。访问违规/进程内内存破坏也不能承诺靠 C++ catch 恢复，必须靠版本固定、校验、测试与故障诊断防范。

### 11.15 后端与质量验收

正式 Windows CPU、正式 Windows Vulkan 分别记录工具链、驱动、硬件、原生/模型版本和性能，不能拿上游 Linux/独立 demo 结果代替。[M02]

验证同一场景下位移规则一致、姿态无明显穿模/左右反转、启停/蹲姿/装备兼容、长时间无泄漏、切换后端和模型失败可恢复到可靠动作。网络游戏不要求异构后端逐骨骼位完全相同，但要求碰撞、命中和技能结果不依赖这种相同性。[M04]

生成动作全部禁用的测试必须同样通过基础玩法；生成动作开启的目标硬件测试也必须通过，缺一不可。

## 12. 人物骨架、动画资源与风格生产管线

### 12.1 正式动画资源清单

| 资源组 | 必需内容 |
|---|---|
| 普通移动 | 待机、走/跑/冲刺、启动/停止、左右转、前后侧移 |
| 蹲姿 | 进入、蹲待机、前后侧蹲走、退出 |
| 腾空 | 起跳、上升、下落、轻落地、重落地 |
| 闪避 | 前/后/左/右侧步或翻滚，结束恢复 |
| 武器 | 单手轻击链、重击、双手动作、盾格挡/招架、装备/收起 |
| 魔法 | 施法前摇、生效姿态、恢复；持不同施法器兼容 |
| 交互 | 拾取、搬运、放下、投掷、救援、低障碍翻越 |
| 受控状态 | 受击、眩晕、倒地/死亡、复活起身 |
| 预览 | 中立待机、对应装备握持与有限转身 |

优先使用已有合法 UE 官方基础动画；缺失动作必须补充经许可可用的基础资源、制作或重定向，不能以“没有素材”为理由用文字或不相关片段代替。所有资源有来源和许可记录，模型/动画可保持基础美术风格。

### 12.2 风格数据生产

上游 `.mbstyle` 是带 G1 拓扑、坐标与张量约束的版本化格式，不是任意 FBX/GLB 改扩展名。[M06] 正式交付一个受控工具链：

源动画 → 统一采样与清理 → 重定向到 G1 source → 正确的世界/局部坐标和 30 FPS 时间 → FK 与特征转换 → 写出 `.mbstyle`/边界姿态资源 → 上游 loader 校验 → UE 回放比较 → 内容审批。

首次覆盖普通移动、蹲姿与侧移等实际生成场景。自定义人物到 G1 的映射存在形体和动作分布差异，必须评估关节限位、重心、脚接触与质量；载入成功不是风格质量证明。质量不合格的动作仍需制作到达标，不能把尚不合格资源设为正式默认。

导出内容必须包含来源资产 ID、来源哈希、骨架哈希、参考姿态、轴向/单位、采样率和风格版本。转换器失败明确中止，不产出“看似成功”的空动作。

### 12.3 重定向与后处理

制作 G1 源 IK Rig 与目标人物 IK Rig，配置根/pelvis、脊柱、四肢、手脚链和参考姿态。[U07] 双手持武器以武器 Grip/辅助握点驱动手 IK，脚部接触根据真实地面和移动基座处理。生成模型未输出的手指采用握持姿态，不让手张开穿过剑柄。

移动速度与步幅匹配，蹲姿 pelvis 高度与胶囊变化匹配；不同体型参数存在独立配置而不是统一缩放全部骨骼。动画曲线/标记由权威动作资料或经过校验的工具生成，不自动推测伤害窗口。

### 12.4 内容验收证据

为普通移动、蹲走、跳跃落地、四向闪避、攻击格挡、施法、拾取搬运、翻越分别记录实际游戏视频。镜头包含侧面脚部、正面左右肢体和近景握持；同时测试 Manny/Quinn 或实际选定的角色配置。

调试视图允许显示源骨架、目标骨架、胶囊、真实轨迹、计划轨迹和姿态接触误差。正式玩家视图不显示这些调试骨架与内部数据。

### 13.1 任务日志

使用任务列表卡片与选中任务详情，分类为主线、支线/委托、已完成；显示目标勾选、计数、奖励图标、状态和追踪按钮。待领奖励以物品集合表示，不继续只支持“金币/材料”两种硬编码汇总。

领取奖励调用统一事务，满包进入持久待领区而非静默丢失。待领奖励记录 RewardId、来源和领取状态，可分批领取且不能重复；不允许通过任务 UI 直接增加 Profile.Gold。日常刷新使用服务器日期和明确时区，并让页面显示剩余刷新信息，不能靠客户端调时重领。

### 13.2 地图

正式交付与实际地图坐标匹配的 2D 地图底图、玩家朝向、队友、任务目标、已知服务和已解锁据点标记，支持缩放、拖动、筛选和标记详情。基础素材地图可以用简洁地形块与图标绘制，但不能只是坐标字符串。

区域未加载不影响持久任务锚点显示；动态目标位置的更新频率有预算。点击据点传送只在规则允许、已解锁、非受限状态下提交，复用加载就绪/安全落点协议，不在 UI 中调用 SetActorLocation。

### 13.3 队伍

显示人物头像/模型摘要、生命/状态、真人或 AI 标识、队长和跟随/等待状态；提供邀请、接受/拒绝、离队、解散 AI 与合法指令。附近玩家列表和实际队伍列表必须分开，不能把地图上所有玩家都当队友。

请求由服务器确认容量、身份和可变更状态；人物死亡/离开/重连后条目正确更新。AI 指令作用于实际 AI 行为，不能只改变页面文本。

### 13.4 设置

图形、音量、镜头、UI 缩放、键位、控制器和动作后端选择均有保存/取消/恢复默认。键位冲突按输入上下文判断，不将 Gameplay 的 Q 与菜单中的 Q 自动视为同一冲突，也不能在同一上下文保留两个危险动作。

动作设置显示当前实际 provider、请求 provider 与兼容降级原因；这些可以放在高级信息中，避免玩家选择 Vulkan 后实际使用传统动画却毫无说明。普通玩家无需接触模型路径、随机种子或原生错误码。

图形分辨率修改有确认/自动恢复机制，避免无法操作的黑屏设置。所有用户设置写独立配置，不与权威任务/金币存档共用保存权限。

<a id="network-world"></a>
## 14. 联机、区域流送与生命周期

### 14.1 权威状态与复制范围

| 数据 | 权威与复制策略 |
|---|---|
| 库存、货币、已学技能、任务 | 服务器权威，owner-only 授权快照/增量 |
| 装备外观、姿态、动作实例 | 服务器确认，向相关客户端复制必要展示数据 |
| 菜单页签、搜索、详情、鼠标选择 | 本地，不复制 |
| 运动位置、速度、移动基座 | CharacterMovement 的预测/纠正流程 |
| MotionBricks 骨骼输出与原生模型 | 客户端表现数据，不作为权威玩法依赖 |
| 世界掉落与领取版本 | 服务器事务与持久世界记录 |
| NPC 对话会话和交易权限 | 服务器验证，本地显示授权内容 |

库存初始容量较小，可以使用有界、类型化、owner-only 快照，不以“必须改 FastArray”代替测量。若采用增量复制，必须有事务版本封装、缺段补全和全量重同步；不能把不同版本的装备与库存拼在一帧后执行操作。

### 14.2 生成动作的联机原则

网络同步动作意图/状态、装备姿态、目标运动参数、动作实例及服务器时间，不高频可靠 RPC 传每个骨骼。相同 seed 不保证不同硬件/后端的动作决策完全相同，[M04] 因此伤害、躲避、碰撞和任务资格不依赖逐骨骼确定性。

远端角色可以在本地生成或使用兼容动画，视觉细节允许差异；所有影响玩法的 root 位移和动作阶段必须一致。需要精确同步的特殊动作使用受控动作定义和同步时间线，而不是要求所有机器重新生成同一段神经动画。

晚加入和重连收到当前姿态、动作状态与时间，能够直接进入正确中间状态；不需要重放从开局开始的全部计划。

### 14.3 专用服务器与 Listen Server

专服构建不链接/加载 MotionBricks 原生库、GGML、Vulkan、UMG 和预览模型；服务器只保留动作规则和必要的轻量契约。若 Gameplay 引用动作组件类型，Server 配置提供不含原生依赖的 stub/契约实现，不能因头文件依赖而把完整推理 DLL 一并拖入。

Listen Server 既是权威游戏实例又有本地视觉客户端，因此只为需要显示的角色创建视觉会话，不对同一个角色创建“服务器一个、客户端一个”的重复模型状态。

### 14.4 角色与会话生命周期

Pawn 被替换时解绑 UI/ASC avatar、停止旧动作、注销旧 motion agent；新 Pawn 恢复档案装备和技能，再创建新视觉会话。角色 ID 可相同但 PawnEpoch 必须不同。旧回调不能访问新 Pawn 的原生 handle。

客户端离开地图、NPC 被卸载、敌人死亡、队友断线、PIE 世界销毁时都释放引用或完成安全注销。菜单打开期间发生 Pawn 更换也必须重新绑定，不留下空白菜单或悬空 PreviewActor。

### 14.5 流送与持久对象

保留当前 World Partition 外壳和运行时区域记录/稳定身份机制；本次补齐与新系统相关的就绪、引用、首次按需装配和卸载回归。当前 v9 记录了“先装配再调度”的限制，不能把它称为全量首次按需加载完成。[G16]

第一次进入区域时按依赖装配当前需要的对象，NPC/容器/任务锚点从稳定定义解析；卸载时保存持久状态、解除对话与交易会话、清理碰撞/水电连接与视觉 motion 会话。持有中/仍参与事务的实体通过有界租约暂时保留，不能由于一个遗失引用永远保活。

地图与任务 UI 引用稳定 ID/锚点，而不是强持有跨区域 Actor。退出区域不删除未领取物品或个人奖励。携带中物品跨区时身份与位置唯一，不重新在出生点生成副本。

离线区域继续采用明确的“状态冻结”策略，不因加入动画系统自动引入离线热/水/电追算。若以后改变世界模拟策略，应单独定义迁移，不混在 UI 重构中。

### 14.6 传送与异常恢复

传送先结束/取消不允许跨区的动作与交互，申请目标资源/碰撞/必要导航就绪，再确认落点；超时回到安全位置。动画 source context 在传送完成后重置，不继续使用旧世界轨迹。

受击、复活或掉落领取与传送竞态，采用同一角色状态版本检查。客户端 UI 可继续看只读数据，写操作等待就绪；不能在等待界面背后偷偷扣款或生成物品。

## 15. 迁移、开发工具与发布管线

### 15.1 存储后端的正式目标

把现有存储适配接口完善为 `ITransactionalStore`，默认本地/专服采用单一 SQLite 事务数据库，包含世界、角色、物品、学习与奖励记录以及有界回执索引。这样跨域变化可处于同一个数据库事务，仍允许将来替换后端。[S01]

采用受控单写队列，IO 不阻塞游戏 Tick；提交前保护涉及的实体版本，提交后按结果发布，不能让候选状态与同期战斗修改互相覆盖。明确队列容量、繁忙重试、磁盘满和失败恢复。

在本地受支持文件系统上使用经验证的日志与同步配置；若采用 WAL，使用 `synchronous=FULL`、有界 checkpoint 和正确备份流程，不放在网络共享文件系统，不把多个 ATTACH 数据库的写入当作一个跨库原子事务。[S02]

记录实际 SQLite 版本及已知修复。官方已记录 2026 年修复的 WAL-reset 问题，不能假设 UE 随附版本已经包含修复；选用包含该修复的版本/回移植构建并验证。[S02] 不将数据库事务保证夸大成硬件损坏后绝不丢数据，仍需备份和完整性检查。

这项后端更换是支撑完整道具/技能/任务事务的正式工作包，不在本次文档生成过程中执行。

### 15.2 存档格式与迁移步骤

新存档清楚区分 SaveSchemaVersion、ContentSchemaVersion、NetworkProtocolVersion、ModelRevision；它们不能共用一个 `Version=10` 数字。存盘使用显式 DTO/schema，不把任意 C++ 字段布局当永久协议。

迁移步骤：

1. 识别旧版本并备份原文件，记录来源版本/哈希。
2. 使用对应旧 reader 解码，执行旧版完整性检查；不使用新结构直接猜读旧二进制。
3. 转换物品、格子、装备、技能、奖励和世界记录，运行新不变量检查。
4. 写入新的事务数据库，在迁移事务中记录已导入标识；验证后才启用新存档。
5. 首次启动进行实际角色恢复；失败保留旧文件和诊断，不覆盖成空白新世界。

Core Redirects 解决反射类/包/属性改名加载引用，不能代替自定义二进制存档的数据转换。移动 UCLASS 所在模块会改变 `/Script/Module.Class` 路径，应写精确重定向并验证 BP/DataAsset/地图引用。[U10]

### 15.3 必需迁移映射

| 旧数据/行为 | 新数据/行为 |
|---|---|
| `Inventory[]` 紧凑数组 | 原序填入固定格，保留所有 InstanceId 与 Count |
| `Equipped[Slot]=InstanceId` | 保留映射；旧单槽定义转 AllowedSlots；校验新的十槽上限 |
| `LearnedSpells` bitmask | 四个基础技能 rank 1 + 旧故事授予来源 |
| `SelectedSpell` 编号 | SkillId 与快捷位，越界值回到合法已授权技能 |
| `PendingGold/PendingMaterial` | 唯一 PendingReward 记录，不能重复生成 |
| 旧成功回执 | 保留拒绝旧请求所需版本；不能迁移为可重新执行状态 |
| 旧用户键位 | 保留显式自定义；旧默认 Space/Ctrl 迁移新默认并提示变化 |
| 旧区域与掉落 | 保持 StableId、位置、已领取记录；不重置整张地图 |
| 旧装备内容资产引用 | 精确路径重定向/重新保存，保留 ItemId |

v9 满包与未知物品不能静默删除。新默认容量不小于旧合法实际占用；确需缩小通过专用溢出保留区处理，并提供领取路径，不直接截断数组。

### 15.4 作者工具与数据校验

交付物品/槽位配置、技能前置编辑、对话配置、图标导入、MotionProfile/风格工具和校验报告入口。批处理必须能发现未知类型、断引用、技能环、缺可取得内容、图标/动画缺失、错误的骨架/单位和打包遗漏。

UE Data Validation 可扩展为项目自定义校验并以命令行执行；Primary Asset 注册/Bundle/软引用用于明确加载与 Cook 范围。[U08]、[U09]

工具生成的 `.uasset`、图标、地图引用与数据配置应作为必要内容提交；生成日志、玩家存档、缓存和凭据不得提交。第三方模型按许可证与制品策略管理，不在普通游戏内容提交中隐式更换版本。

### 15.5 构建与发布通道

每次开发提交优先增量编译、小型规则测试和针对性启动，遵循当前仓库轻量验证约定；最终发布候选必须安排独立的完整 Cook/Package、长时和多人验收。二者不能相互替代。[G17]

交付以下脚本能力（名称为拟新增/整理后的目标，不表示仓库已有）：

```text
BuildNativeMotion      # 固定版本构建、CPU/Vulkan、导出符号校验
PrepareMotionBundle    # 显式下载/制品获取、哈希、许可与文件清单
ValidateContent        # 库存、技能、对话、图标、动画、打包引用
TestGameplayRules      # 小型确定性规则回归
TestMenuInteraction    # 键鼠/控制器/分辨率与事务交互
TestMotionIntegration  # 真推理、重定向、时序、后端和故障
MigrateSaveDryRun       # 只读扫描、转换报告，不覆盖真实存档
PackageClientServer    # Shipping 客户端与专服，资源/依赖 Stage
CollectAcceptance      # 汇总准确版本、命令、报告、截图/视频索引
```

纯净机器从发布包启动，不安装 UE Editor、Python、Go 或开发 Vulkan SDK；需要的系统运行库与驱动要求写入说明。模型/风格和所有 DLL 使用发布包相对路径，不能读取开发者绝对路径或原仓库 `generated/`。

### 15.6 许可与来源

根据上游说明，移植代码为 Apache 2.0，原始/转换权重和相关风格分发仍遵循 NVIDIA Open Model License，并有其他第三方许可。[M01] 发布时保留相应协议、NOTICE/归属与模型来源清单，按实际采用版本逐项核对，不把“代码 Apache”误当“模型和所有素材都能无条件再分发”。

记录官方 UE 素材、自制图标、动画与转换风格来源。数据转换不会自动消除原始资源的许可限制。存在未确认再分发权限的必需资源时属于发布阻塞，不以临时下载链接绕过。

同一提交聚焦一个可回归的职责：机械移动/包含路径、类型拆分、协议、存储、某个页面或某组动作。不要将全目录迁移、技能语义变化与第三方推理升级混在一次巨大提交。

每个提交写清实际改动、执行过的测试、没有执行的测试和迁移影响；代码及必要内容资产一起提交。不能用未运行的截图名称或计划中的测试数量填“通过”。遵守非强推、保留他人改动与现有分支协作规则。[G17]

### 16.2 阶段边界

架构/数据阶段结束时应可恢复旧玩法；UI/成长阶段结束时应能从正常存档完整操作；动作阶段结束时兼容路径与生成路径都进入正式地图；发布阶段结束时所有章节的功能、资源、故障和性能门槛同时满足。

### 17.3 拟定性能与体验预算

以下是拟定发布门槛，应在 V10-01 中对实际目标硬件和场景锁定。它们不是上游保证，也不是本次实测结果。若最低硬件确需修改，须明确变更支持范围/质量档案并重新验收，不能仅把失败测量隐藏在兼容路径里。

| 指标 | 目标/判定 |
|---|---|
| 正式目标客户端帧率 | 标准 1080p 质量档以 60 FPS 为目标，记录 P50/P95/P99 帧时间与卡顿，不只平均帧率 |
| 菜单输入可见反馈 | 正常运行下下一帧或不超过 2 帧；网络事务即时显示处理中，不假装已成功 |
| 首次打开菜单 | 预载后 ≤200 ms 出现可操作页面；冷加载分开记录，不同步加载整套装备资源 |
| UI 额外游戏线程开销 | 标准库存/技能/地图场景 P95 ≤1 ms，关闭后没有全页面刷新 Tick |
| 生成姿态桥接游戏线程开销 | 不含后台推理，P95 ≤0.3 ms；禁止阻塞等待 |
| 本地角色动作规则响应 | 跳/蹲/闪避/受击不等待生成，正常运行下 ≤2 帧开始正确反馈 |
| 本地角色有效新计划延迟 | 支持的生成硬件档上提交到可用计划 P95 ≤150 ms；急剧状态变化仍遵守即时兼容响应 |
| 生成缓冲与队列 | 每 agent 在途 1 + 待处理最新 1，有界输出环；不无限积压 |
| 推理预算/利用率 | 实测 P99 推理与重规划周期留安全余量；记录 batch、风格、时长，不引用 SONIC 指标 |
| 内存/显存 | 模型按预算共享，稳定热身后不持续单调增长；分别记录峰值与长时平台值 |
| 预览成本 | 关闭页面停止 SceneCapture；不因打开背包额外加载全世界或多份模型 |
| 网络 | 私有库存 owner-only，不传逐骨骼可靠流；统计带宽、RPC 率和重试率 |

最低兼容硬件必须完整运行传统动画；正式声明支持生成动作的 CPU/GPU 档还必须通过其生成门槛。对外说明清楚这两个范围，不能用“所有机器都有 fallback”推导“所有机器都支持实时生成”。

### 17.4 长时与故障测试

发布候选执行至少 60 分钟混合游玩/流送测试，以及 100 次菜单开关、50 次角色重生/区域切换的定向循环，检查 native handles、Widget/PreviewActor、RenderTarget、ASC 效果与待处理命令的数量是否回到稳定基线。

执行 IO 失败、磁盘满、模拟进程中止、复制延迟、资源迟到、模型损坏与后端不可用测试。测试时长和次数是正式 QA 规格，不表示本文已经执行。

### 17.5 证据格式

每份验收记录必须包含：游戏源码提交、原生库/子模块/模型版本、引擎/工具链、硬件和驱动、构建配置、测试用例 ID、实际命令/步骤、结果、日志、截图或视频索引、已知限制。

截图必须来自实际运行页面；不能拿 UMG Designer 布局、概念图或硬编码演示数据证明运行正确。MotionBricks 证据必须包含真实调用计数/时间与输入变化，不能只贴有动作的人物视频。

“代码已写”“局部检查通过”“集成测试通过”“发布验收通过”分开记录。发生失败如实写失败，修复后重测相关集合，不修改历史记录冒充首次通过。

## 18. 风险处理与发布完成定义

### 18.1 风险必须变成具体工程任务

| 风险 | 必须采取的处理 | 不能使用的替代说法 |
|---|---|---|
| G1 与人物骨架差异大 | 源骨架、参考姿态、IK 链、坐标/接触测试和风格质量迭代 | “把骨骼数组复制过去就能用” |
| 生成耗时超过预算 | 优化调度/线程/图、限制高质量实例、验证适配档；仍完成正式支持档 | “有 CPU 后端所以肯定实时” |
| C++23 与 UE 工具链差异 | 原生独立构建、C ABI、版本锁与运行库验证 | “把所有模块改成 C++23” |
| DX12 渲染与 Vulkan 推理竞争 | 实测独立设备/队列资源与驱动，提供经验证 CPU/传统路径 | “Vulkan 后端即与 UE RHI 无缝共享” |
| 共享模型并发与借用内存 | 单一调度所有权、深拷贝结果、在途调用退出协议 | “模型是只读的，所以随便并行” |
| 旧存档与反射迁移 | 旧 reader、转换事务、精确 Redirect、备份/恢复 | “改字段后 SerializeBin 会自己兼容” |
| UI 图形齐全但数据不通 | 完整玩家路径与服务器回执测试 | “截图上有格子就算背包完成” |
| 源码平铺转移为新巨型模块 | 依赖规则、状态所有权、功能扩展测试 | “已经建了文件夹所以完成解耦” |
| 原生资源遗漏 | Stage 清单、哈希与纯净机器 Shipping 启动 | “编辑器能跑就一定能发布” |
| 模型/素材许可不明确 | 按固定版本确认再分发要求与归属文件 | “开源项目里找到的都能打包” |

### 18.2 必须同时满足的发布完成定义

**架构：**目标模块边界真实成立；新增同机制内容不修改主角/巨型分支；运行时不依赖编辑器，服务器不依赖 UI 和生成推理。

**界面：**背包看到真实角色预览、全部开放装备槽和物品格子；顶部导航及全部已开放页面完整操作；每个物品、装备和技能均可通过右键/控制器打开详细资料。

**玩法：**库存、装备属性、耐久修理、容器、拾取丢弃、商店、技能学习升级重置、NPC 对话与任务追踪、基础动作与主线全部形成可达闭环。

**动作：**跳跃、下蹲、闪避相互独立且符合碰撞；受控动画完整；MotionBricks 在声明支持档上真实参与正式角色动作，具有非阻塞调度、正确重定向、状态切换和故障恢复。

**数据：**旧档迁移不丢合法物品和已学技能；跨域事务、重试、崩溃恢复和联机权限正确；冷启动、重连和重生能够重建一致状态。

**发布：**真实 Cook/Shipping 客户端与专服通过；所有必要资源、模型、库依赖与许可在包内；性能与长时报告完整；测试结果绑定准确版本。

任何一条未满足，只能标记对应功能未完成或未验收，不以“后续完善”“已有接口”“演示正常”替代。

### 18.3 不要求无边界扩展

完整可用不等于一次实现所有 RPG 功能。本方案不要求无限装备词条、任意人体骨架无需适配、任意对象自动生成物理交互、全平台实时神经动画、复杂联网账号或全部地图内容生产。系统扩展点必须明确，已承诺和已开放的功能必须完成。

**最终交付判断只看玩家能否正常使用、服务器能否正确执行、存档能否稳定恢复和发布包能否可靠运行，不以新增文件数、插件数或演示窗口数判断。**


每个开放装备槽至少两件可比较、可取得样本；四系技能每系三级，全部等级有实际效果与取得路径；至少一个普通背景人物、一个有闲聊 NPC、一个前置服务 NPC、一个导师、一个商人、一个仓储/战利品容器和一个可并发领取掉落。内容资产通过同一正式数据链提供，不仅存在测试代码中。
